d1-pages-starter: conectando GitHub Pages con SQLite serverless mediante Cloudflare D1 y Workers

Publicado: 12 de octubre de 2026. Categoría: Sistemas & Cloud. Tiempo de lectura: ~5 min
Etiquetas: SQLite, Cloudflare D1, Cloudflare Workers, GitHub Pages, CLI, Serverless

Cada vez que quiero armar una herramienta pequeña, un tablero de notas, un registro de correos o un widget interactivo para la web, me gusta mantener dos reglas claras: cero costos fijos mensuales y cero servidores que tener que parchar a las tres de la mañana.

Para el frontend, GitHub Pages resuelve casi todo: alojamiento estático gratuito, CDN global rápido, despliegues automáticos desde Git y 100 GB de transferencia mensual. Pero en cuanto necesitas que los usuarios interactúen y guarden datos de verdad, te chocas contra la pared clásica de la web estática: no hay base de datos donde escribir.

Durante mucho tiempo la recomendación por defecto para proyectos personales fue PlanetScale, hasta que en abril de 2024 eliminaron su plan gratuito y pasaron a cobrar un mínimo de 39 dólares al mes. Tampoco sirve meter un archivo .sqlite directo en el repositorio de GitHub Pages: aunque existen experimentos con WebAssembly (sql.js-httpvfs) para hacer consultas de solo lectura con peticiones HTTP Range, un archivo en GitHub Pages es público por definición (cualquiera puede descargarse la base de datos entera) y los servidores estáticos rechazan peticiones POST o PUT, impidiendo que los usuarios guarden datos.

Para resolver este problema de raíz construí d1-pages-starter: una arquitectura edge que conecta GitHub Pages con Cloudflare D1 (SQLite nativo serverless) utilizando Cloudflare Workers como gateway seguro, acompañada de un CLI interactivo para inicializar proyectos en segundos.

1. La arquitectura: puente edge entre GitHub Pages y D1

La idea central es separar estrictamente la entrega estática de la persistencia de datos. El navegador descarga el HTML, CSS y JavaScript desde GitHub Pages, y luego realiza peticiones REST al Cloudflare Worker, que se encarga de la validación, los encabezados CORS y la ejecución de sentencias SQL preparadas sobre Cloudflare D1.

1. Navegador del Visitante
  • Descarga interfaz estática (HTML, CSS, JS)
GitHub Pages (Alojamiento) ││ Cloudflare Worker (Gateway)
  • CDN global estático ││ - Valida tipos y longitudes
  • 100 GB/mes de ancho banda ││ - Restringe orígenes con CORS
  • 0 ms de arranque en frío ││ - Conexión nativa env.DB
▼
Cloudflare D1 (SQLite Edge)
  • Sentencias preparadas SQL
  • 5 GB almacenamiento
  • 5M lecturas / 100k escrit.

Esta estructura tiene tres ventajas técnicas clave:

  1. Cero credenciales en el cliente: Los navegadores nunca ven una contraseña, token o cadena de conexión a la base de datos. D1 se vincula al Worker de forma nativa mediante env.DB, por lo que no existen secretos que puedan filtrarse en bundles de JavaScript.
  2. Cero costos de infraestructura: GitHub Pages ofrece 100 GB/mes de transferencia; Cloudflare Workers incluye 100.000 peticiones diarias gratuitas; y Cloudflare D1 ofrece 5 GB de almacenamiento, 5 millones de lecturas y 100.000 escrituras al día. Para proyectos personales, herramientas de equipo o prototipos, el costo es de cero dólares al mes.
  3. Emulación local sin conexión: Con Wrangler puedes ejecutar wrangler d1 execute --local para inicializar y probar tu base de datos SQLite directamente en tu máquina local sin enviar un solo paquete a la nube.

2. Soporte multilenguaje: TypeScript, Rust y Python

Aunque TypeScript suele ser la opción habitual en Cloudflare Workers, no estás atado a un solo runtime. Gracias a WebAssembly, el Worker puede compilarse directamente en Rust usando worker-rs, ofreciendo seguridad de tipos estricta y bajo consumo de memoria con soporte nativo para D1:

use worker::*;
use serde::{Deserialize, Serialize};

#[event(fetch)]
async fn fetch(req: Request, env: Env, _ctx: Context) -> Result<Response> {
    let d1 = env.d1("DB")?;
    let stmt = d1.prepare("SELECT id, name, message FROM posts ORDER BY id DESC LIMIT 50");
    let results = stmt.all().await?.results::<serde_json::Value>()?;
    Response::from_json(&serde_json::json!({ "success": true, "data": results }))
}

Para quienes prefieren scripts ligeros sin tooling complejo, Cloudflare Workers también soporta Python nativo mediante Pyodide en WebAssembly.

3. Un CLI interactivo para inicializar en segundos

Para no tener que copiar carpetas a mano ni pelearse con configuraciones de Wrangler, empaqueté un CLI interactivo inspirado en bun create dentro del repositorio:

# Con bun:
bun create d1-pages mi-app

# Con npx:
npx create-d1-pages mi-app

# O directamente desde el repositorio:
node bin/cli.js

El asistente interactivo guía paso a paso al desarrollador por terminal:

  • Base de datos: Cloudflare D1 (SQLite nativo) o Turso (libSQL distribuido).
  • Lenguaje del backend: TypeScript, Rust (WebAssembly) o Python.
  • Frontend: Vanilla JS (cero pasos de compilación), React con Vite y Tailwind CSS, Astro (sitio estático con islas interactivas) o Svelte 5 con runes.
  • Plantilla de datos: Libro de visitas / feed, formulario de lista de espera con validación, o contadores atómicos de votos y visitas.
  • CI/CD: Generación automática de flujos de GitHub Actions para desplegar tanto GitHub Pages como el Worker en Cloudflare con cada git push.

El proyecto completo, el código del CLI y todas las plantillas están disponibles en código abierto en github.com/riccivr/d1-pages-starter con licencia MIT.

d1-pages-starter: connecting GitHub Pages with serverless SQLite using Cloudflare D1 and Workers

Published: October 12, 2026. Category: Systems & Cloud. Reading time: ~5 min
Tags: SQLite, Cloudflare D1, Cloudflare Workers, GitHub Pages, CLI, Serverless

Whenever I want to build a small utility, note board, waitlist, or interactive web widget, I stick to two rules: zero monthly hosting bills and zero virtual machines to maintain.

For the frontend, GitHub Pages handles almost everything: free static hosting, fast global CDN delivery, automated git-based deployments, and 100 GB of monthly bandwidth. But the moment you need visitor interaction and persistent data storage, you hit the traditional barrier of static websites: there is no database to write to.

For a long time, the standard recommendation for hobby projects was PlanetScale, until they discontinued their free tier in April 2024 and introduced a $39/month minimum plan. Committing a raw .sqlite file directly into a GitHub Pages repository is also not a viable solution for user writes. While experiments with WebAssembly (sql.js-httpvfs) permit read-only querying over HTTP Range requests, files on GitHub Pages are public by definition (anyone can download the entire database), and static file servers reject POST or PUT requests, making runtime writes impossible.

To solve this directly, I built d1-pages-starter: an edge architecture that connects GitHub Pages to Cloudflare D1 (serverless native SQLite) using Cloudflare Workers as a secure gateway, accompanied by an interactive CLI to initialize projects in seconds.

1. The architecture: an edge bridge between GitHub Pages and D1

The core model cleanly decouples static asset delivery from data persistence. Visitors download HTML, CSS, and client-side JavaScript from GitHub Pages, then make REST requests to a Cloudflare Worker that validates payloads, enforces CORS boundaries, and runs prepared SQL statements against Cloudflare D1.

1. Visitor Browser
  • Downloads static UI bundle (HTML, CSS, JS)
GitHub Pages (Hosting) ││ Cloudflare Worker (Gateway)
  • Global static CDN ││ - Validates lengths & types
  • 100 GB/month bandwidth ││ - Restricts CORS origins
  • Zero cold starts ││ - Native env.DB binding
▼
Cloudflare D1 (Edge SQLite)
  • Prepared SQL queries
  • 5 GB storage
  • 5M reads / 100k writes/day

This layout brings three specific technical advantages:

  1. Zero client-side secrets: Browser clients never receive database credentials or connection tokens. D1 binds natively to the Worker runtime through env.DB, preventing accidental secret leaks in frontend bundles.
  2. Zero infrastructure cost: GitHub Pages provides 100 GB/month of egress; Cloudflare Workers includes 100,000 requests per day on the free tier; and Cloudflare D1 offers 5 GB of storage, 5 million reads, and 100,000 writes daily. For side projects, prototypes, or internal tools, total hosting cost is zero dollars.
  3. Offline local emulation: Using Wrangler, running wrangler d1 execute --local initializes and tests SQLite tables directly on your local machine without sending network traffic to cloud services.

2. Multi-language runtimes: TypeScript, Rust, and Python

While TypeScript is common on Cloudflare Workers, you are not restricted to JavaScript. Because Workers run on V8 with WebAssembly support, you can compile backends directly in Rust using worker-rs, delivering memory safety, low resource overhead, and native D1 database bindings:

use worker::*;
use serde::{Deserialize, Serialize};

#[event(fetch)]
async fn fetch(req: Request, env: Env, _ctx: Context) -> Result<Response> {
    let d1 = env.d1("DB")?;
    let stmt = d1.prepare("SELECT id, name, message FROM posts ORDER BY id DESC LIMIT 50");
    let results = stmt.all().await?.results::<serde_json::Value>()?;
    Response::from_json(&serde_json::json!({ "success": true, "data": results }))
}

For developers who prefer concise scripting without heavy build toolchains, Cloudflare Workers also natively supports Python through Pyodide.

3. An interactive scaffolding CLI

To avoid manual directory copying and Wrangler configuration, the repository includes an interactive terminal CLI inspired by bun create:

# Using bun:
bun create d1-pages my-app

# Using npx:
npx create-d1-pages my-app

# Directly from the repository:
node bin/cli.js

The terminal prompts step through:

  • Database: Cloudflare D1 (native SQLite) or Turso (distributed libSQL).
  • Backend runtime: TypeScript, Rust (WebAssembly), or Python.
  • Frontend: Vanilla JS (zero build step), React with Vite and Tailwind CSS, Astro (static site with interactive islands), or Svelte 5 with runes.
  • Schema preset: Community guestbook, waitlist signup with validation, or atomic counters for votes and views.
  • CI/CD: Automated GitHub Actions workflows to deploy both GitHub Pages and Cloudflare Workers on git push.

The project, CLI tool, and templates are open source under the MIT license at github.com/riccivr/d1-pages-starter.
